# 人工评审与案例工作台设计规格

日期：2026-09-20  
状态：已确认，待实施计划

## 1. 背景与目标

跨文化表达实验室已经能够基于已发布术语、英语译法、来源证据和文化提示生成结构化表达报告，但当前结果只存在于浏览器内，无法进入人工审核、版本比较和研究统计流程。

本阶段新增“人工评审与案例工作台”，把一次性 AI 输出转化为可保存、可修订、可审核、可追溯和可导出的研究案例，形成：

`表达实验室生成 → 保存案例 → 人工修订 → 审核 → 归档 → 研究导出`

首版面向项目组本地或受控网络使用，不建设用户登录体系。审核人由研究人员手动填写；公开部署前必须增加身份认证和权限控制。

## 2. 范围

### 2.1 本期包含

- 从表达实验室手动保存当前报告为案例。
- 保存不可变的 AI 报告快照、传播任务、系统警告和关联术语。
- 人工编辑最终表达、填写评审意见、审核人和问题标签。
- 每次人工修改生成一条不可覆盖的修订记录。
- 草稿、待审核、已通过、已归档状态流转。
- 案例列表、组合筛选、详情、AI/人工对照和修订历史。
- JSON 与 CSV 研究数据导出。
- 重复保存、非法状态跳转和并发覆盖保护。
- 数据库迁移、API 文档、使用说明和自动化测试。

### 2.2 本期不包含

- 账号、登录、角色权限和电子签名。
- 公开分享链接和匿名协作。
- 删除案例或修订记录。
- 自动把人工定稿写回术语推荐译法。
- AI 自动复审、评分或准确率计算。
- 法语、西班牙语、俄语和阿拉伯语评审流程。
- 批量导入外部案例。

## 3. 方案选择

采用“案例快照 + 追加式修订记录”。

AI 快照在案例创建时保存，之后不能通过普通业务接口修改。人工定稿、评审意见、审核人和问题标签保存在修订记录中，每次保存均追加新版本。该方案比只保存最终结果多保留了人工干预过程，又避免把报告每个字段过早拆成大量表。

## 4. 身份与部署边界

首版不提供登录。`reviewer_name` 是人工填写的研究字段，不代表经过认证的用户身份，也不得在界面或导出中描述为数字签名。

工作台只适合：

- 单机演示；
- 项目组局域网；
- 已由外部网关控制访问的环境。

生产公开部署前必须增加认证、授权、审计主体和共享限流存储。本期文档必须明确这一限制。

## 5. 数据模型

### 5.1 ReviewCase

表名：`review_cases`

字段：

- `id`：整数主键。
- `public_id`：不可猜测、唯一的公开编号，用于 API 和导出文件名。
- `title`：案例标题，1—200 字。
- `source_request_id`：表达实验室请求编号，用于幂等保存。
- `source_text`：中文原文，10—1000 字。
- `target_language`：首版固定为 `en`。
- `audience`、`scenario`、`style`、`locale`：沿用表达实验室固定枚举。
- `ai_snapshot`：通过现有 `ExpressionAnalysis` 契约验证后的完整 JSON 快照。
- `status`：`draft | pending_review | approved | archived`。
- `current_revision_number`：当前最新修订号，用于乐观并发控制。
- `created_at`、`updated_at`：UTC 时间。

约束：

- `source_request_id` 唯一，重复保存返回已有案例，不重复插入。
- `ai_snapshot` 创建后不可通过普通接口更新。
- 不提供物理删除接口。

### 5.2 ReviewRevision

表名：`review_revisions`

字段：

- `id`：整数主键。
- `case_id`：关联案例。
- `revision_number`：案例内从 1 递增。
- `final_expression`：人工定稿，1—2000 字。
- `review_notes`：评审意见，最多 5000 字。
- `reviewer_name`：审核人姓名，最多 100 字。
- `issue_tags`：固定标签数组。
- `created_at`：UTC 时间。

约束：`case_id + revision_number` 唯一。修订记录只能新增，不能更新或删除。

案例创建时生成第 1 条初始修订，其 `final_expression` 默认为 AI 首选表达，`review_notes`、`reviewer_name` 和 `issue_tags` 为空。

### 5.3 ReviewCaseTerm

表名：`review_case_terms`

字段：

- `case_id`：关联案例。
- `term_id`：关联现有 `kb_terms`。
- `position`：保留表达实验室选择顺序。

组合主键为 `case_id + term_id`。创建案例时只接受仍然存在且已发布的术语。

### 5.4 ReviewEvent

表名：`review_events`

用于记录状态变更，不记录完整敏感正文。

字段：

- `id`、`case_id`。
- `event_type`：`created | submitted | approved | returned | archived | restored`。
- `from_status`、`to_status`。
- `reviewer_name`：执行状态操作时填写的姓名。
- `note`：简短状态说明，最多 1000 字。
- `created_at`。

事件只新增、不修改、不删除。

## 6. 固定问题标签

前后端共享以下稳定枚举：

- `literal_translation`：直译痕迹。
- `terminology_inconsistency`：术语不一致。
- `cultural_misreading`：文化误读。
- `register_mismatch`：语域不符。
- `ambiguity`：表意不清。
- `unnatural_english`：英语不自然。
- `citation_gap`：引用依据不足。
- `other`：其他。

接口只接受枚举值；界面和导出负责映射中文标签。

## 7. 状态机

允许的状态变更：

| 当前状态 | 操作 | 目标状态 | 前置条件 |
|---|---|---|---|
| `draft` | submit | `pending_review` | 最新修订包含非空人工定稿和审核人 |
| `pending_review` | approve | `approved` | 操作人姓名非空 |
| `pending_review` | return | `draft` | 操作人姓名和退回说明非空 |
| `approved` | reopen | `draft` | 操作人姓名和说明非空 |
| `approved` | archive | `archived` | 操作人姓名非空 |
| `archived` | restore | `approved` | 操作人姓名非空 |

除表中路径外的变更均返回 HTTP 409。归档案例只读，恢复后才能修订。已通过案例退回草稿后，下一次编辑必须生成新的修订版本。

## 8. API 设计

所有接口使用 `{code, message, data}` 信封，错误内容不包含数据库或完整正文。

### 8.1 POST /api/v1/review-cases

输入：

- `title`
- `term_ids`
- 表达实验室返回的 `ExpressionAnalysis`

服务端重新使用 Pydantic 契约验证快照，确认 `review_status=ai_unreviewed`、术语存在且已发布、快照中的术语引用属于所选术语。`source_request_id` 已存在时返回原案例并标记 `created=false`。

成功：201；幂等重复：200。

### 8.2 GET /api/v1/review-cases

分页参数：`page`、`page_size`。可选筛选：

- `status`
- `term_id`
- `reviewer`
- `issue_tag`
- `q`（案例标题和中文原文）

返回案例摘要、当前修订摘要、术语摘要和分页元数据。默认按 `updated_at` 倒序。

### 8.3 GET /api/v1/review-cases/{public_id}

返回案例 AI 快照、关联术语、当前修订、完整修订历史和状态事件。不存在返回 404。

### 8.4 POST /api/v1/review-cases/{public_id}/revisions

输入：

- `expected_revision_number`
- `final_expression`
- `review_notes`
- `reviewer_name`
- `issue_tags`

仅 `draft`、`pending_review` 和 `approved` 可新增修订；`archived` 返回 409。`expected_revision_number` 与服务器不一致时返回 409，客户端必须刷新后再决定是否重新提交。

### 8.5 POST /api/v1/review-cases/{public_id}/transitions

输入：

- `action`
- `expected_revision_number`
- `reviewer_name`
- `note`

按状态机验证并新增 `ReviewEvent`。状态变化和事件写入同一数据库事务。

### 8.6 GET /api/v1/review-cases/export

支持 `format=json|csv`，并复用列表筛选参数。JSON 导出完整研究数据；CSV 每个案例一行，包含任务条件、AI 首选表达、当前人工定稿、状态、审核人、问题标签、修订次数和时间字段。

CSV 使用 UTF-8 BOM，避免中文在 Excel 中乱码；所有以 `= + - @` 开头的单元格内容需要前置单引号，防止公式注入。

## 9. 前端设计

### 9.1 表达实验室

成功报告区域新增“保存到研究工作台”。点击后打开轻量对话框，只要求填写案例标题。保存中禁止重复提交；成功后显示案例编号和“进入工作台”链接。幂等重复保存直接跳转已有案例。

保存失败不得清除当前表达任务或报告。

### 9.2 研究工作台 `/workspace`

页面包含：

1. 概览区：草稿、待审核、已通过、已归档数量和平均修订次数。
2. 筛选区：关键词、状态、术语、审核人、问题标签。
3. 案例队列：标题、术语、状态、审核人、更新时间和修订次数。
4. 评审详情：AI 初稿与当前人工定稿并排对照。
5. 评审表单：定稿、意见、审核人和问题标签。
6. 修订历史：逐版查看定稿、标签、意见、审核人和时间。
7. 状态操作：根据当前状态只显示允许的动作。
8. 导出：按当前筛选条件下载 JSON 或 CSV。

桌面端使用列表/详情双栏；移动端先显示列表，进入案例后显示详情。所有状态、标签和风险提示都同时使用文字，不只依赖颜色。

## 10. 数据流与事务

### 10.1 保存案例

1. 前端提交标题、术语 ID 和当前分析结果。
2. 服务端校验请求大小、结构、枚举、术语和快照。
3. 在单一事务中创建 `ReviewCase`、术语关联、初始修订和 `created` 事件。
4. 唯一键冲突按幂等重复处理，不插入第二份案例。

### 10.2 保存修订

1. 前端携带当前看到的修订号。
2. 服务端锁定或原子校验案例当前修订号。
3. 不一致返回 409；一致则插入下一条修订并更新案例当前修订号。
4. 任一步失败时事务整体回滚。

### 10.3 状态变更

1. 校验当前状态、操作、修订完整性和执行人字段。
2. 更新状态并新增事件。
3. 两项操作在同一事务提交。

## 11. 错误处理与安全

- 所有写接口限制 JSON 请求体大小并要求 JSON Content-Type。
- 标题、定稿、意见、审核人和状态说明均限制长度并去除首尾空白。
- 服务端不信任客户端传入的术语名称、来源元数据和状态。
- 日志只记录不透明案例编号、状态码和异常类型，不记录完整原文、AI 快照或评审意见。
- 导出文件名只使用案例公开编号或 UTC 时间，不使用用户正文。
- CSV 防公式注入，前端继续按文本节点渲染所有模型与人工内容。
- 无登录版本不声称具有真实身份审计能力。
- 暂不提供删除接口，避免不可恢复的数据损失。

## 12. 测试与验收

### 12.1 后端测试

- 模型约束、级联关系、唯一键和迁移升级。
- 案例创建、幂等重复和未发布术语拒绝。
- AI 快照结构、ID 和状态校验。
- 修订追加、版本冲突和归档只读。
- 所有合法/非法状态变更。
- 列表分页及组合筛选。
- JSON/CSV 导出、中文编码和公式注入防护。
- 成功与失败事务均不产生半成品数据。
- 错误响应和日志不泄露正文。

### 12.2 前端测试

- 表达实验室保存对话框、幂等反馈和失败保留报告。
- `/workspace` 路由替换占位页。
- 概览、筛选、分页、案例选择和空状态。
- AI/人工对照、固定标签和修订历史。
- 非法状态动作不可见，合法操作调用正确接口。
- 409 冲突提示刷新，不静默覆盖。
- JSON/CSV 下载不触发额外写请求。
- HTML 字符串仍作为文本显示。
- 桌面与移动语义结构、键盘操作和可访问性状态。

### 12.3 完成标准

- 能从表达实验室保存案例并立即在工作台找到。
- 能完成草稿、提交、通过、退回、再修订、归档和恢复流程。
- AI 初稿不可修改，人工修订历史逐版保留。
- 能按状态、术语、审核人和问题标签筛选。
- JSON/CSV 导出可直接用于后续研究统计。
- 页面刷新后案例仍存在。
- 重复保存、非法跳转和并发覆盖均有稳定处理。
- 数据库迁移不改写现有术语知识数据。
- 全量后端和前端测试、编译、构建及密钥扫描通过。

## 13. 实施顺序

1. 契约、模型和数据库迁移。
2. 案例服务、状态机、导出和 API。
3. 前端类型与 API 客户端。
4. 表达实验室保存入口。
5. 研究工作台列表、详情、修订和状态操作。
6. 导出、文档、安全验证和最终验收。
