# 中国特色话语跨文化表达与多语知识研究平台重构设计

## 1 项目定位

本项目从面向公众的术语查询网站，重构为以跨文化表达研究为核心、以多语术语知识库为基础、以轻量研究工作台为内容治理入口的多语知识研究平台。

平台重点回答的问题不再是“一个术语的英文是什么”，而是：面对特定语种、受众和传播场景，中国特色概念应如何准确、自然、有效地表达，并能说明推荐依据、文化差异和使用边界。

软件用于固化外国语言学、翻译研究和跨文化传播的研究过程，不以复杂算法、模型训练或技术堆叠作为项目价值来源。

## 2 设计目标

### 2.1 核心目标

1. 将现有扁平术语记录升级为包含译法、来源、例句、场景、文化说明和概念关系的知识档案。
2. 建立跨文化表达实验室，使用户能针对语种、受众和场景获得有依据的表达建议。
3. 建立从内容编辑、复核到发布的轻量治理流程，并保留修订历史。
4. 将淮河文化重构为地域文化国际传播示范专题，验证平台方法的可迁移性。
5. 形成可用于中期检查、论文、软著和结题答辩的过程数据与成果指标。

### 2.2 非目标

第一阶段不建设以下内容：

- 自研或训练 BERT、BiLSTM 等模型。
- 小程序、原生移动应用和线下终端。
- 微服务、MongoDB、Neo4j、区块链等非必要基础设施。
- 自动发布未经人工确认的 AI 内容。
- 十余种语言的全面覆盖。
- 仅用于视觉展示的 3D 地球或无真实关系数据支撑的知识图谱。

## 3 目标用户与优先级

### 3.1 第一用户

- 项目组内容编辑人员。
- 翻译学习者和语言研究人员。
- 承担术语复核工作的指导教师或审核人员。

第一用户需要完成语料整理、译法比较、文化说明、内容复核和成果统计。

### 3.2 第二用户

- 对中国特色话语感兴趣的普通公众。
- 海外用户和国际传播内容使用者。
- 文化、教育和文旅场景中的内容使用者。

第二用户主要浏览经审核发布的知识档案、文化专题和场景化表达结果，不接触内部治理功能。

## 4 设计原则

1. **概念优先**：一个概念可以有多个中文名称、多个语种译法和多个场景表达，不能继续使用“一条记录一个翻译字段”的模型。
2. **来源优先**：正式译法、定义和文化说明必须能够关联出处；AI 生成内容不能伪装成权威来源。
3. **场景优先**：表达建议必须说明面向的语种、受众、传播场景和风格。
4. **人工负责**：AI 提供检索、比较、起草和风险提醒，编辑者与审核者承担最终责任。
5. **过程可追溯**：发布内容保留审核状态、修改理由、操作者和版本记录。
6. **研究可度量**：平台操作产生可以统计的研究数据，而不仅是页面访问量。
7. **适度工程化**：保留 React、Flask 和 MySQL，优先改善领域模型、模块边界和测试，不为技术新颖而重写。

## 5 总体产品结构

平台分为三个相互连接的空间。

```text
公共知识门户
  首页 术语探索 术语知识档案 文化专题 淮河示范专题
                         ↑
跨文化表达实验室
  术语 语种 受众 场景 风格 → 表达建议 文化风险 来源依据
                         ↑
研究工作台
  来源管理 术语编辑 多语译法 文化说明 复核发布 修订历史
```

研究工作台生产和维护内容；跨文化表达实验室消费已发布知识并生成辅助建议；公共知识门户展示审核后的成果。

## 6 信息架构与页面

### 6.1 公共知识门户

#### 首页 `/`

首页负责建立项目身份和引导核心任务，不直接堆叠完整术语列表。内容包括：

- 项目定位与核心研究问题。
- 统一搜索入口。
- 三层术语体系概览。
- 跨文化表达实验室入口。
- 精选术语知识档案。
- 文化专题与淮河示范专题。
- 研究成果摘要。

#### 术语探索 `/discover`

支持关键词、语种、层级、文化类别、使用场景和专题筛选。结果项展示术语名称、核心定义、推荐译法、层级、来源数量和已覆盖语种，不展示编辑与删除按钮。

#### 术语知识档案 `/terms/:id`

术语详情从弹窗升级为独立页面，包含：

- 概念摘要。
- 中文名称与别名。
- 多语译法及其状态。
- 适用场景和例句。
- 权威来源与证据片段。
- 跨文化理解提示与常见误译。
- 相关概念。
- 所属专题。
- 最近审核与修订信息。

#### 文化专题 `/topics` 与 `/topics/:slug`

专题用于组织一组术语、人物、文献和文化叙事。淮河文化使用统一专题模型建设，不再作为与主库割裂的独立数据岛。

### 6.2 跨文化表达实验室 `/lab`

实验室是平台最具辨识度的核心功能。

用户输入：

- 术语或概念。
- 目标语种。
- 目标受众。
- 使用场景。
- 表达风格。

系统输出：

- 推荐表达。
- 简明解释。
- 场景化示例。
- 文化背景。
- 潜在误读与规避建议。
- 已收录译法对比。
- 支撑建议的来源列表。
- “AI 辅助建议，需人工判断”的状态提示。

第一阶段预设场景为政策外宣、学术研究、新闻传播、文旅讲解、海外公众和儿童友好表达。用户不能把未审核的生成结果直接发布到公共术语库。

### 6.3 研究工作台 `/workspace`

工作台只向登录用户开放，第一阶段设置编辑者和审核者两类角色。

#### 来源管理 `/workspace/sources`

登记文献名称、发布机构、日期、语种、链接或出版信息、权威等级、正文或摘录、采集人和所属专题。

#### 术语管理 `/workspace/terms`

以列表和分步编辑器管理术语概念、译法、来源、场景和文化说明。删除采用归档方式，已发布内容不进行不可恢复的物理删除。

#### 复核中心 `/workspace/reviews`

审核者查看待复核内容、字段差异、来源证据和编辑说明，执行通过、退回或请求补充来源。

#### 成果驾驶舱 `/workspace/insights`

展示语料数量、术语数量、覆盖语种、已审校译法比例、文化说明覆盖率、专题进度、译法冲突、修订次数和 AI 建议采纳情况。

## 7 内容生命周期

术语采用以下状态：

```text
草稿 → 待复核 → 退回修改 → 待发布 → 已发布 → 修订中 → 已归档
```

规则如下：

- 编辑者创建和修改草稿，提交复核时必须至少包含中文名称、定义、层级和一个来源。
- 审核者可以通过或退回，并必须为退回填写意见。
- 只有通过审核的版本才能发布到公共门户。
- 对已发布术语的修改创建新修订，不直接覆盖公开版本。
- 归档内容不再公开展示，但保留历史记录和引用关系。

## 8 数据模型

### 8.1 核心实体

#### `terms`

- `id`
- `preferred_name_zh`
- `definition_zh`
- `cultural_connotation`
- `term_level`
- `culture_category`
- `status`
- `current_version`
- `created_by`
- `created_at`
- `updated_at`
- `published_at`

#### `term_names`

保存中文别名、旧称和缩略语，避免把同一概念的多个中文名称压入主表。非中文表达统一进入 `translations`。

#### `languages`

保存语言代码、中文名称、英文名称和启用状态。

#### `translations`

- 关联术语与语言。
- 译文。
- 译法类型：推荐、可接受、历史、不推荐。
- 权威等级。
- 适用地区。
- 审核状态。
- 说明。

#### `sources`

保存文献题名、机构、日期、语种、来源类型、链接或出版信息、权威等级和正文摘要。

#### `term_evidence`

连接术语、译法与来源，保存原文片段、对应译文、页码或段落位置及说明。

#### `contexts`

保存场景、受众、表达风格和推荐使用说明。

#### `translation_contexts`

连接译法与场景，记录推荐程度和例句。

#### `cultural_notes`

保存目标文化、理解差异、直译风险、错误联想和表达建议。

#### `term_relations`

保存上位、下位、相关、同义、历史演变等关系。

#### `topics` 与 `topic_items`

组织淮河文化等专题及其关联术语、人物、文献和中药材内容。

#### `revisions` 与 `reviews`

保存版本快照、字段差异、修改理由、审核意见、操作者和时间。

#### `users`

保存登录名、密码摘要、显示名称、角色、启用状态和最近登录时间。第一阶段不保存与业务无关的个人资料。

### 8.2 第一阶段简化

第一阶段不实现通用工作流引擎。状态转换由服务层规则控制；版本记录保存业务字段快照；关系数据继续使用 MySQL 邻接表，不引入图数据库。

## 9 AI 设计

### 9.1 服务边界

DeepSeek 被封装为独立 AI 服务，路由和业务代码不直接拼装长提示词。AI 服务接收结构化任务，返回经过校验的结构化结果。

首批任务包括：

- 根据已发布术语资料生成场景化表达建议。
- 对比多个既有译法并总结差异。
- 起草简明文化背景说明。
- 提示潜在文化误读。
- 检查术语档案中缺失的来源或字段。

### 9.2 上下文来源

第一阶段不建设向量数据库。系统使用关系数据库完成精确术语检索，并将以下内容组装为上下文：

- 术语定义与文化内涵。
- 已审核译法。
- 对应场景和例句。
- 来源证据片段。
- 文化说明和风险提示。

当没有足够的本库资料时，系统明确提示“当前依据不足”，不让模型虚构权威出处。

### 9.3 输出与安全

- 输出展示 AI 标识和生成时间。
- 生成结果不自动进入正式知识库。
- 后端记录任务类型和模型名称，但不记录 API Key。
- 上游错误向用户转换为通用提示，详细错误只进入服务端日志。
- AI 返回必须通过结构校验；不完整结果以降级形式展示。

## 10 技术架构

### 10.1 后端

保留 Flask，将单文件应用逐步拆分为：

```text
term-backend/
  app/
    __init__.py
    config.py
    extensions.py
    models/
    schemas/
    routes/
    services/
    repositories/
    ai/
  migrations/
  scripts/
  tests/
  run.py
```

- `routes` 处理 HTTP 输入输出。
- `services` 承担状态转换、发布、修订和表达实验室业务规则。
- `repositories` 封装查询。
- `schemas` 负责请求和响应校验。
- `ai` 封装 DeepSeek 客户端、提示构建和输出解析。
- `models` 只描述持久化结构。

数据库继续使用 MySQL，并引入可重复执行的数据迁移。旧入口在迁移期保留兼容层，前端切换完成后再移除。

### 10.2 前端

保留 React、TypeScript、Vite 和 Ant Design，但减少大面积内联样式，采用页面、领域组件、服务和设计令牌分层：

```text
term-frontend/src/
  app/
  pages/
  features/
    discovery/
    term-profile/
    expression-lab/
    workspace/
    topics/
  components/
  services/
  types/
  styles/
```

术语详情、实验室和工作台各自拥有独立领域组件。公共页面与工作台使用不同布局，但共享术语、来源和语言类型。

## 12 权限设计

第一阶段角色：

- `editor`：创建和编辑草稿、提交复核。
- `reviewer`：拥有编辑者权限，并能审核、发布和归档。

公共读取接口无需登录；工作台写接口必须登录并校验角色。第一阶段采用服务端会话：登录成功后由后端设置 `HttpOnly`、`SameSite=Lax` 的会话 Cookie，生产环境启用 `Secure`；写操作进行 CSRF 防护。不引入第三方身份平台，也不把访问令牌保存到浏览器本地存储。

## 13 视觉方向

视觉风格强调学术、文化和可信度，不采用政务网站模板，也不采用娱乐化国潮装饰。

- 主色使用深海军蓝或墨蓝。
- 辅色使用克制的朱砂色。
- 背景使用暖白和浅灰，正文保持高对比度。
- 中文标题可使用合适的宋体或衬线字体，正文使用清晰的无衬线字体。
- 数据、来源、状态和审核信息优先使用清晰排版，不依赖大量卡片。
- 动效只用于状态变化、关系探索和页面过渡。
- 支持键盘操作、可见焦点、语义标签和移动端布局。

## 14 错误处理与降级

- 数据库或 API 失败时，公共页面展示明确的重试状态，不显示空白页。
- AI 不可用时，术语知识档案和公共检索仍可正常使用。
- 表达实验室在 AI 失败时仍展示已有译法、场景和来源。
- 无足够来源时，不生成“权威推荐”，而显示依据不足。
- 表单验证错误定位到具体字段；审核状态冲突返回可理解的业务错误。
- 已发布版本修改冲突时拒绝静默覆盖，要求刷新后重新提交。

## 15 数据迁移

1. 为现有数据库创建备份。
2. 创建新表和必要索引，不立即删除旧表。
3. 将现有术语字段迁移到概念、译法和来源结构。
4. 将小语种混合字段作为待整理记录导入，并标记为未审核。
5. 将淮河术语、人物和中药材映射到淮河专题。
6. 对迁移数量、关键字段和抽样记录进行验证。
7. 新前端切换到 v1 API 后，再决定旧写接口和旧表的退役时间。

迁移必须可重复执行，并在失败时回滚；不直接对唯一生产数据进行不可逆操作。

## 16 测试策略

### 16.1 后端

- 模型约束和序列化测试。
- 术语状态转换测试。
- 发布版本与修订历史测试。
- 权限和未授权写入测试。
- 旧数据迁移测试。
- 表达实验室上下文构建和 AI 降级测试。
- API 集成测试。

所有外部 AI 调用在自动化测试中使用边界替身；另保留显式执行的最小真实连接检查，不放入默认测试套件。

### 16.2 前端

- 核心组件与表单交互测试。
- 搜索筛选和分页状态测试。
- 术语知识档案渲染测试。
- 表达实验室成功、依据不足和 AI 失败场景测试。
- 工作台状态转换与权限显示测试。
- 关键流程端到端测试。

### 16.3 数据与内容

- 迁移前后数量核对。
- 多语译法与语言代码完整性检查。
- 来源链接和证据关联检查。
- 重点术语人工抽样复核。

## 17 分阶段实施

### 第一阶段 核心平台

1. 建立新后端结构、配置与测试基线。
2. 建立核心数据模型与迁移脚本。
3. 迁移现有术语和淮河数据。
4. 重做应用外壳、首页、术语探索和知识档案。
5. 完成跨文化表达实验室 MVP。
6. 完成来源、多语译法和文化提示的基础编辑能力。
7. 加入登录、角色和基础安全配置。

### 第二阶段 研究治理

1. 完成提交、复核、发布和修订流程。
2. 建立专题内容管理与淮河示范专题。
3. 增加概念关系和相关术语探索。
4. 建设研究成果驾驶舱。
5. 完成用户测试和无障碍优化。

### 第三阶段 成果验证

1. 扩充代表性小语种和重点术语案例。
2. 开展场景化表达理解度测试。
3. 整理研究指标、案例报告和工程化建设手册素材。
4. 完善部署、备份、监控和成果展示。

## 18 第一阶段验收标准

第一阶段完成时必须满足：

1. 现有术语与淮河数据完成可验证迁移，无记录静默丢失。
2. 公共用户能够搜索、筛选并浏览完整术语知识档案。
3. 术语能够关联多个语种译法、来源证据、场景和文化说明。
4. 表达实验室能够基于本库资料生成带来源提示的场景化建议。
5. AI 不可用时，检索和知识档案功能仍可使用。
6. 编辑者能够创建和维护未发布内容，公共用户不能访问工作台写接口。
7. 前后端核心测试、构建和静态检查通过。
8. 密钥和本地配置不进入 Git 跟踪文件。
9. 页面在桌面和常见移动宽度下可正常使用。
10. README、环境变量示例和 API 文档与实现一致。

## 19 已确认的关键决策

- 项目主线是跨文化表达研究，不是高精度算法研发。
- 第一用户是项目组、翻译学习者和研究人员，普通公众为第二用户。
- 跨文化表达实验室是核心差异化功能。
- 术语生产与审核闭环是内容基础设施。
- DeepSeek 是当前 AI 服务提供方，模型通过环境变量配置。
- 保留 React、Flask 和 MySQL，不进行无必要的技术栈重写。
- 先完成 Web 核心闭环，再考虑小程序、离线终端和更多语种。
