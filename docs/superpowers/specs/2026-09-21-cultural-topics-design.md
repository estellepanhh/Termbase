# 文化专题模块设计

## 背景与目标

当前平台已经具备术语发现、术语档案、表达实验室和人工复核工作台，但“文化专题”路由仍是占位页面。数据库中已有 `Topic` 与 `TopicItem` 模型，遗留数据导入也会建立“淮河文化”专题，因此本轮不再建设一套孤立展示页，而是把已有数据能力接成可持续扩展的公开专题系统。

首版目标是形成“专题总览—专题详情—术语档案”的完整研究浏览链路，并以“淮河文化”作为首个正式专题。以后新增“文明交流互鉴”“非遗外译”等专题时，应主要补充数据，而不需要重新开发页面。

## 范围

本轮包含：

- 已发布专题的公开列表与详情接口；
- 专题元信息、统计数据和条目的安全序列化；
- 文化专题总览页与通用专题详情页；
- 首页、术语档案、专题页面之间的双向导航；
- 中英文界面文案、儿童模式、大字模式和移动端适配；
- 后端接口测试、前端服务与页面测试、路由测试；
- 淮河文化专题的基础简介补全。

本轮不包含：

- 专题内容管理后台或通用 CMS；
- AI 自动生成专题正文；
- 登录、收藏、评论等用户系统；
- 地图、时间轴、关系图谱等高成本可视化；
- 为数量而创建缺乏内容的空专题；
- 数据库排序字段迁移。

## 总体架构

采用数据驱动的通用专题模板：

```text
Topic / TopicItem
        ↓
专题查询与序列化服务
        ↓
GET /api/topics
GET /api/topics/<slug>
        ↓
专题总览 / 通用专题详情
        ↓
术语档案
```

`Topic` 保存专题标题、标识、简介和发布状态；`TopicItem` 保存专题内的术语或扩展条目。后端负责访问控制、统计和字段收敛，前端只消费稳定的公开结构，不直接理解遗留表字段。

首版继续使用现有数据表，不新增数据库迁移。条目按类型和稳定的数据顺序排列，为未来增加人工排序字段保留空间，但不提前建设编辑系统。

## 后端设计

### 查询服务

新增独立的公开专题查询服务，职责包括：

- 仅查询 `status = published` 的专题；
- 汇总专题的条目总数、关联术语数量和各条目类型数量；
- 加载专题条目及其关联术语，避免逐条查询；
- 排除未发布术语；
- 将遗留 `payload` 收敛为允许公开展示的字段；
- 生成稳定、可测试的返回顺序。

专题查询逻辑不放入路由函数，路由只负责参数、HTTP 状态和 JSON 响应。这样未来管理端或其他展示渠道可以复用相同服务边界。

### 专题列表接口

`GET /api/topics`

仅返回已发布专题。每项包括：

- `slug`
- `title`
- `summary`
- `item_count`
- `term_count`
- `entry_type_counts`

列表接口不携带全部条目，避免总览页响应随专题内容线性膨胀。

### 专题详情接口

`GET /api/topics/<slug>`

返回：

- 专题基础信息；
- 与列表接口一致的统计信息；
- 经过分组和排序的公开条目。

关联术语条目包含：

- 专题条目 ID 与标题；
- 术语 ID；
- 中英文名称；
- 分类；
- 简短释义；
- 可用的代表性译文。

非术语条目包含：

- 专题条目 ID；
- 条目类型；
- 标题；
- 从 `payload` 白名单中提取的公开字段。

原始 `payload` 不整体返回，防止历史导入数据中的内部字段、格式噪声或未来敏感字段意外进入公开接口。

### 发布规则与异常

- 草稿专题对公开接口表现为不存在，返回 404；
- 不存在的专题返回 404；
- 草稿术语不出现在专题详情中；
- 单个条目字段缺失时返回空值或省略可选字段，不使整个专题请求失败；
- 路由层沿用项目现有的统一错误响应格式。

### 淮河文化初始化

遗留导入继续负责创建或更新 `huaihe-culture` 专题，并保证其状态为 `published`。当专题简介为空时，导入逻辑写入一段稳定的项目级简介；已有人工简介不得被覆盖。

## 前端设计

### 路由

- `/topics`：文化专题总览；
- `/topics/:slug`：通用专题详情；
- `/huaihe`：重定向到 `/topics/huaihe-culture`；
- 术语档案中的专题链接改为对应详情路由。

### 专题总览

总览页由三部分组成：

1. 研究导语：说明专题如何把术语、地域文化与多语传播材料组织成研究单元；
2. 数据概览：显示已发布专题数量及总体收录规模；
3. 专题卡片列表：展示标题、简介、条目总数、术语数量和内容类型，整张卡片可进入详情。

页面沿用现有纸张色、靛青和朱红编辑风格，避免回到通用后台卡片视觉。无已发布专题时展示解释性空状态，而不是“建设中”。

### 专题详情

详情页包含：

- 专题标题与摘要；
- 条目数量、术语数量和内容类型概览；
- 页面内分区导航；
- “核心术语”研究型列表；
- 人物、地点、文化等扩展条目分区；
- 返回专题总览的路径。

核心术语条目显示中英文名称、分类、释义摘要和代表性译文，并链接到现有术语档案。扩展条目根据 `entry_type` 使用一致的内容骨架呈现，不为每种条目建立独立页面。

### 阅读模式与响应式

- 大字模式继续依赖现有全局字号机制；
- 儿童模式使用更直白的分区标题与辅助说明，但不改写研究数据；
- 桌面端可采用导语与统计并列、内容分区纵向展开；
- 移动端统一为单栏，页内导航横向滚动或紧凑换行；
- 长标题、长译文和遗留内容必须允许自然换行，不产生横向溢出。

### 页面状态

- 加载：使用与页面结构一致的轻量骨架；
- 空数据：解释当前专题尚无可公开条目，并提供返回入口；
- 网络错误：显示错误说明和重试按钮；
- 404：显示专题不存在或尚未发布，并提供返回专题总览的操作。

## 前端代码边界

建议按职责拆分：

- `features/topics/TopicsPage`：专题总览容器；
- `features/topics/TopicDetailPage`：专题详情容器；
- `features/topics/components`：专题卡片、统计、分区和条目展示；
- `services/knowledgeApi`：专题列表和详情请求；
- `types/knowledge`：公开专题 DTO 类型。

容器负责请求与页面状态，展示组件只接收数据。条目类型到展示标签、分组顺序的映射集中管理，避免散落在 JSX 条件分支中。

## 测试策略

后端测试覆盖：

- 列表只返回已发布专题；
- 列表统计正确；
- 详情返回标准化的术语与扩展条目；
- 草稿术语被排除；
- 草稿专题和未知标识返回 404；
- 原始 `payload` 中非白名单字段不会公开；
- 遗留导入补充默认简介但不覆盖人工简介。

前端测试覆盖：

- 请求函数与响应类型；
- 总览加载、成功、空数据和错误状态；
- 详情分区、统计和术语链接；
- 404 与重试交互；
- 儿童模式文案；
- `/topics`、`/topics/:slug` 与 `/huaihe` 路由行为。

实现完成后集中运行后端完整测试、前端完整测试、lint 与生产构建。用户要求优先开发效率，因此中途仅运行与当前改动直接相关的快速测试，最终再做完整验证。

## 验收标准

- 访问 `/topics` 不再看到占位页，而能看到已发布专题；
- 可以从专题总览进入淮河文化详情；
- 专题详情能区分术语与其他文化条目，并展示真实数据库内容；
- 可以从专题进入术语档案，并从术语档案返回对应专题；
- 草稿内容不会通过公开专题接口泄露；
- 手机宽度、儿童模式和大字模式下页面均可正常阅读；
- 新增一个符合现有模型的已发布专题后，无需新增前端页面代码即可展示；
- 后端测试、前端测试、lint 和生产构建全部通过。
